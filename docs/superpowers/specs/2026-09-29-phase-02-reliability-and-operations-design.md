# Phase 2 안정화와 교육 운영 보완 설계

작성일: 2026-09-29  
상태: 설계 승인됨 · 구현 계획 작성 전

## 1. 목적과 성공 기준

Phase 2의 교육과정, 차수, 신청, 승인, 나의 학습, 사용자 관리 화면을 실제 Supabase 데이터로 안정적으로 운영한다. 교육담당자는 차수의 모집 상태를 직접 전환하고, 참가자는 한국 시간 기준의 모집 기간 안에서 `open` 차수만 신청한다.

완료 시 다음을 만족한다.

- Vercel Production에서 서버 전용 Supabase 키가 유효하게 주입되어 데이터 조회 화면이 500 없이 응답한다.
- 차수는 `draft → open → closed → completed` 또는 `cancelled`로 상태를 전환할 수 있다.
- `datetime-local` 입력값은 Asia/Seoul로 해석하고, 저장·비교는 UTC instant로 일관되게 수행한다.
- 홈의 예정 교육·수료 이력·승인 대기 수가 로그인 사용자와 역할에 맞는 실제 집계값을 표시한다.
- 일반 사용자에게는 안전한 한국어 오류 안내를 표시하고 상세 진단은 서버 로그에만 남긴다.
- 데모/테스트 데이터는 가명과 테스트용 사번을 쓰며, 운영 프로필 원본을 임의로 변경하지 않는다.

## 2. 확인된 현황과 원인

Vercel Production 로그에서 `/courses` 요청이 `SUPABASE_SECRET_KEY` 빈 문자열에 대한 `ZodError`로 실패했다. 데이터 조회 화면은 모두 `createAdminSupabaseClient()`를 호출하고, 이 함수는 서버 전용 환경 변수 검증을 통과해야 한다. 로그인과 비밀번호 변경 흐름은 이 관리 클라이언트를 요구하지 않아 정상 동작했다.

Vercel에 변수 이름은 존재하지만 배포 런타임에 유효한 값이 전달되지 않는 것이 직접 원인이다. Supabase 원격 마이그레이션 세 개는 적용되어 있으며, 현재 오류는 테이블 미생성이나 RLS 오류가 아니다.

## 3. 범위와 비범위

### 범위

- Vercel Production/Preview의 `SUPABASE_SECRET_KEY`를 올바른 서버 전용 Secret으로 재설정하고 재배포한다.
- 데이터 조회 실패를 포털 오류 경계와 각 서버 조회의 명시적 오류 처리로 사용자 친화적으로 처리한다.
- 차수 상태 전환 UI·서버 액션·검증을 추가한다.
- KST 입력/출력/기한 비교 공통 유틸을 추가하고 기존 차수·신청·취소 화면에 적용한다.
- 역할별 홈 집계를 서버에서 계산한다.
- 테스트 데이터 생성 규칙과 개인정보 표시 원칙을 문서화하고 가명 샘플만 추가한다.

### 비범위

- 참가자 직접 배정, 일정 충돌, 수료 이력 차단의 신규 구현은 이번 안정화 범위에 포함하지 않는다.
- 실제 구성원의 이름·사번을 가명으로 일괄 치환하지 않는다.
- 브라우저에 Supabase Secret Key를 제공하거나 클라이언트용 관리 API를 만들지 않는다.

## 4. 설계 결정

### 4.1 서버 데이터 접근과 오류 처리

관리자 Secret Key는 Vercel의 Production 및 Preview Secret에만 둔다. `NEXT_PUBLIC_` 접두사를 절대 사용하지 않는다. 배포 직후 `/api/health`, 로그인 화면, 인증된 데이터 화면을 확인한다.

조회 페이지는 Supabase 오류를 무시하고 빈 목록으로 렌더링하지 않는다. 데이터 접근 실패는 서버에서 원인과 경로를 기록하고 오류 경계로 전달한다. `src/app/(portal)/error.tsx`는 한국어 재시도 안내와 로그인 화면으로 돌아가는 동작을 제공한다. Secret, SQL 원문, 사용자 개인정보는 화면 또는 클라이언트 로그에 출력하지 않는다.

서버 액션의 권한 확인은 기존 `requireUser()`와 과정 담당자 검사를 유지한다. 화면 조회도 시스템 관리자 전체 조회, 교육담당자 담당 과정 조회, 참가자 본인 데이터 조회로 범위를 제한한다.

### 4.2 차수 상태 전환

차수 생성 시 상태는 계속 `draft`로 시작한다. 차수 목록 행에 상태 선택과 변경 버튼을 둔다. 교육담당자는 자신에게 배정된 과정 차수만, 시스템 관리자는 모든 차수의 상태를 변경할 수 있다.

허용 전환은 다음과 같다.

| 현재 | 가능한 다음 상태 |
| --- | --- |
| `draft` | `open`, `cancelled` |
| `open` | `closed`, `cancelled` |
| `closed` | `open`, `completed`, `cancelled` |
| `completed` | 없음 |
| `cancelled` | 없음 |

`open`만 참가자 교육 목록에 표시한다. 상태 변경 후 `/admin/sessions`, `/courses`, 홈 관련 경로를 재검증한다. DB enum은 유지하고, 허용 전환 규칙은 재사용 가능한 서비스 함수와 서버 액션에서 함께 검증한다.

### 4.3 한국 표준시

브라우저의 `datetime-local` 문자열은 시간대 정보가 없으므로 서버 UTC 환경에서 `new Date(value)`로 바로 변환하면 9시간 차이가 난다. 공통 시간 모듈은 다음 계약을 제공한다.

- `parseKstDateTime(input: string): Date`: `YYYY-MM-DDTHH:mm`을 Asia/Seoul의 `+09:00`으로 해석한다.
- `toKstIso(input: string): string`: 위 Date를 UTC ISO 문자열로 저장한다.
- `formatKst(value: string | Date, locale): string`: 어떤 서버 지역에서도 `Asia/Seoul`로 표시한다.
- `isKstDeadlineOpen(deadline, now)`: 저장된 UTC instant를 비교하며, 비교 기준은 사용자가 입력한 KST 의도와 일치한다.

차수 스키마, 신청 개시/마감 판정, 취소 가능 판정, 목록 출력, 홈 집계의 날짜 조건에 공통 모듈을 사용한다. 데이터베이스 `timestamptz`에는 UTC instant를 저장한다.

### 4.4 홈 집계

홈은 로그인 사용자에 따라 아래 값을 서버에서 계산한다.

| 카드 | 참가자 | 교육담당자 | 시스템 관리자 |
| --- | --- | --- | --- |
| 예정 교육 | 본인의 `approved` 상태이면서 시작 전인 차수 | 담당 과정의 시작 전 차수 | 전체 시작 전 차수 |
| 수료 이력 | 현재는 `completed` 상태 차수의 본인 승인 신청 수 | 담당 과정의 완료 차수 수 | 전체 완료 차수 수 |
| 승인 대기 | 본인에게 적용 없음, `0` | 담당 과정의 `pending`·`waiting` 신청 수 | 전체 `pending`·`waiting` 신청 수 |

수료 테이블이 Phase 3에서 도입되면 두 번째 카드는 `completions` 기준으로 교체한다. 이 전에는 “완료 차수”라는 표시 문구를 사용해 수료로 오인하지 않게 한다.

### 4.5 테스트 데이터와 개인정보

개발/데모 데이터는 `테스트 사용자 01`, `교육담당자 테스트`처럼 가명을 사용하고, 실제 사번과 구별되는 테스트 식별자만 사용한다. 운영 데이터의 이름·사번은 업무 목적과 권한 범위에서만 표시한다. 목록은 참가자에게 타인의 프로필을 노출하지 않고, 교육담당자·시스템 관리자 화면만 신청자의 이름과 사번을 표시한다.

가명 시드 또는 문서 예제는 실제 운영 계정과 분리하며, 현존 프로필을 수정하지 않는다.

## 5. 검증 전략

- 환경 변수: 배포 후 Production 런타임에서 Secret Key 누락이 아닌 성공적인 데이터 조회를 확인한다.
- 차수: 유효한 상태 전환은 통과하고 완료·취소 차수의 재개방은 거절되는 단위 테스트를 작성한다.
- 시간: `2026-10-01T09:00`이 `2026-10-01T00:00:00.000Z`로 저장되고 한국 시간 09:00으로 표시되는 테스트를 작성한다.
- 집계: 역할별 리포지터리에 입력된 차수/신청 데이터로 각 카드 수를 검증한다.
- 오류: 데이터 접근 예외에 오류 경계의 한글 안내가 표시되고 Secret 값이 렌더링되지 않음을 검증한다.
- 회귀: 전체 Vitest, lint, typecheck, production build, Vercel 배포 후 `/api/health`와 인증 흐름을 검증한다.

## 6. 구현 순서

1. Vercel Secret 재설정 및 런타임 데이터 조회 복구
2. 한국 표준시 공통 모듈과 차수 입력/표시 교체
3. 차수 상태 전환 서비스·액션·관리 화면
4. 역할별 홈 집계와 문구 조정
5. 오류 경계, 조회 오류 처리, 가명 테스트 데이터 문서
6. 전체 검증, 기능 단위 커밋, Git push, Vercel Production 재배포

## 7. 보안 제약

- `SUPABASE_SECRET_KEY`는 Vercel Secret과 서버 전용 모듈에서만 읽는다.
- 모든 사용자 입력은 Zod로 검증한다.
- 차수 변경 및 집계용 조회 모두 로그인 역할과 과정 담당 범위를 확인한다.
- 에러 화면·테스트 출력·Git 이력에 키, SQL 연결 문자열, 실제 사용자 개인정보를 기록하지 않는다.
